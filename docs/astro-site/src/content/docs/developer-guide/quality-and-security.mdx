title: Quality and Security Harness
description: Local and hosted quality, security, and release controls for voiage
---

`voiage` treats repository automation as a release surface. The local harness
and GitHub workflows therefore validate both Python behavior and the controls
that protect changes, dependencies, and published artifacts.

## Local gates

Run affected checks during iteration and the complete gate once for the final candidate:

```sh
tox run-parallel -p 2
```

For local acceptance runs, wrap that same gate in the resource guard using the
verified repository interpreter and a work directory on a volume with space:

```sh
.venv/bin/python scripts/guard_verification.py \
  --work-dir .conductor/local/guarded-acceptance \
  -- .venv/bin/tox run-parallel -p 2
```

The guard samples combined process-group RSS every two seconds, stops the job
above 4 GiB, after one hour, or below 2 GiB free in its work or temporary volume.
It places temporary files in a unique sibling of the checkout on the same
volume, cleans them after successful runs, limits native thread pools, and writes
`resource-report.json` with the peak sampled RSS and termination reason. A limit
exit is a failed gate, never acceptance evidence. Increase a limit only after
reviewing the recorded workload. Coverage uses two workers. Sampling cannot
prevent a brief allocation spike; subprocesses must retain their process group.
The guard only terminates its own isolated group, including leftover children.
It disables detached Git file-monitor daemons for the job through a process-local
override, preserving existing Git settings and shared repository configuration.

The harness is included in tox; a second standalone harness run is unnecessary.
Record the tested tree, environment and result. Reuse successful local evidence
when these inputs remain unchanged. A new runtime, dependency, shared-fixture or
test-infrastructure change requires broader validation. Hosted required checks
remain bound to the current PR revision. Batch edits before pushing, rebase
locally with signed commits, and inspect the actual failed gate before changing
a branch; repeated pushes restart hosted validation.

The `harness` tox environment checks that workflows declare explicit
permissions, external actions are pinned to immutable commits, required
security workflows exist, and repository governance files are present. The
full tox environment additionally runs linting, type checking, docs, contract
validation, the supported Python matrix, and the coverage threshold.

The pre-commit, local and hosted `ty` checks use the same rule policy. The earlier
`unresolved-attribute` exclusion covered both missing attributes and missing
union-member attributes; the current tool names those rules separately.

The installed-provider consumer test uses a private download cache by default
and ignores an inherited `UV_CACHE_DIR`. To reuse an existing writable cache
deliberately, locate it with `uv cache dir`, then set
`VOIAGE_TEST_UV_CACHE_DIR` to that directory when running pytest or tox. This
reuses dependency downloads only: each test still builds the real wheels,
creates a fresh consumer environment, copies installed files, and probes the
public SDK outside the checkout. It does not disable dependency resolution or
make the test offline. Each build, install, and probe has a ten-minute timeout.

Reuse follows [uv's cache-safety contract](https://docs.astral.sh/uv/concepts/cache/#cache-safety);
do not manually change files inside that cache.

The DOCX validator tests use an isolated NuGet cache by default. To reuse a
writable cache owned by the current verification run, set
`VOIAGE_DOCX_TEST_NUGET_CACHE` to its absolute path before running pytest or tox.

For dependency-only changes, also run `uvx --from pip-audit pip-audit --local
--progress-spinner off` and `pnpm audit --prod` from `docs/astro-site`.

Before starting a local gate in a shared checkout, check whether another task
already owns a running tox process and its result log. Coordinate reuse of that
run instead of launching a second process against the same `.tox` directory.
Use the same tox executable and interpreter for follow-up environments: mixing
global and repository-managed tox processes can recreate each other's caches.
If an independent run is necessary, give it a separate work directory. Do not
stop another task's process or treat its pending result as a pass.

## Dependency and experimental-feature policy

### Resolved vulnerability evidence

The P0 Grype callers use the shared, immutable `repository-standards` action.
Pull-request and monitoring findings are advisory. Candidate release gates use
the Critical threshold; scanner, database, inventory and evidence errors fail
both modes. Existing pip-audit, RustSec, privacy, version, scientific and native
qualification checks remain required.

The full `polyglot.sbom.cdx.json` remains the signed release inventory. Its R and
Julia dependency declarations are not exact resolved package versions.
`prepare_grype_sbom.py` therefore creates a separate
`resolved-grype.sbom.cdx.json` containing exact Python and Cargo identities. The
coverage receipt records every excluded R/Julia component and the original
document's SHA-256. Unexpected ecosystems or unresolved Python/Cargo identities
fail preparation. This scoped projection makes no complete R, Julia, operating
system or platform-native dependency claim.

Before TestPyPI or PyPI publication, the reviewed-payload job downloads the
actual staged distributions and retained evidence. It verifies each distribution's
SBOM attestation with the expected repository, signer workflow and signed-tag
source commit, then checks the release manifest, subject hashes and exact full
SBOM predicate. It recomputes and compares the resolved projection before scanning
it. Candidate builds or post-publication scans alone cannot satisfy this gate.
The reviewed distribution hashes remain checked by the existing publication jobs.

The locked crates.io release route separately scans its resolved Cargo inventory
before credentials and publication. Caller-owned binding evidence and shared
scan evidence are retained separately, including failure outcomes. The weekly
released-asset workflow resolves the latest published non-prerelease release
once and checks the retained resolved SBOM's asset ID and GitHub-provided SHA-256.
Missing assets fail explicitly; current-source rebuilding is not released-byte
monitoring. The first qualified retained asset and hosted caller runs remain
acceptance requirements after this configuration is merged.

The supported Python 3.15.2 range tracks compatible stable dependencies and
commits `uv.lock` for reproducibility. Before dependency or runtime changes,
run `uv lock --upgrade` and `python scripts/dependency_frontier.py . --strict`.

Apache Arrow/Parquet is the canonical public tabular interchange; JSON Lines
is an explicit human-debug format. Experimental serializers, JAX, NumPyro,
accelerators, and distributed runtimes remain behind named extras and require
round-trip, numerical-equivalence, provenance, and CPU-reference evidence
before promotion. Python free-threading remains an observation lane rather
than a release or performance claim.

Standardized-ingestion benchmarks use generated, bounded local fixtures and
record stages, input dimensions, and memory rather than enforcing elapsed-time
budgets. They cover only the strict Croissant CSV and Frictionless local
CSV/JSON/Parquet/Arrow profiles; they are not evidence about network transport,
remote catalogues, or upstream parser performance.

## GitHub gates

The prose check invokes Bash and Vale directly, and the repository harness uses
only the pinned Python standard library. Tox-only jobs bootstrap from the locked
`verification` group; tox still creates the installed-package test environments.
After that bootstrap, `uv run --frozen --no-sync` keeps the outer environment
limited to its tooling. C15 telemetry/oracles install the CI and producer-test
dependencies and require JAX and Polars imports before running all oracle cases.
The unrelated experimental database and serializers are not installed there.

Dependency review and shard qualification cancel older revisions of the same
PR. Their merge-group and manual runs have independent concurrency groups.
Runner queue time and job execution time are measured separately; fewer setup
steps do not establish a fixed end-to-end speedup under changing runner load.

The hosted repository runs CodeQL, OpenSSF Scorecard, Dependency Review, and
Zizmor. Workflows also enforce SHA-pinned actions, least-privilege
permissions, disabled credential persistence on security-sensitive checkouts,
and release artifact provenance attestations. The release workflow also
publishes the signed SLSA bundle as a `.intoto.jsonl` release asset so
independent tools can discover provenance without privileged access to
GitHub's attestation store.

Selected GitHub-hosted jobs use the pinned StepSecurity Harden-Runner action in
audit mode. Its agent sends telemetry to StepSecurity and can record network
destinations, file-write paths, and process names and arguments; audit mode
does not block outbound traffic. Do not put credentials in process arguments.
The canonical-sync and conda proposal jobs use the GitHub CLI credential
protocol, and the code-scanning gates read their token from the environment.
The Julia TagBot job is excluded from this monitoring because its
[pinned action constructs a token-bearing Git clone argument](https://github.com/JuliaRegistries/TagBot/blob/6b7c22e7bc2b8f4d1c56b7199a63421cf2667ed1/tagbot/action/git.py#L86-L92).
Reassess that exclusion when the action changes. An action commit pin does not
by itself pin every agent binary it downloads; see the vendor's
[architecture description](https://github.com/step-security/harden-runner/blob/main/docs/how-it-works.md).

The protected `main` ruleset requires pull requests, resolved review threads,
successful required checks, signed commits, and linear history. The required
approval count is zero for the single-maintainer operating model; CODEOWNERS
still routes review responsibility without creating an impossible independent
approval gate. Hosted settings must be verified through the GitHub API because
they are not represented by files in the checkout.

OpenSSF's aggregate Scorecard is interpreted check by check. Independent human
review and multi-organisation contributor diversity are useful signals, but a
single-maintainer project cannot manufacture either signal. The repository
therefore retains zero required approvals while requiring the complete
automated matrix, signed commits, current branches, resolved threads, and
immutable releases. Those deliberate exceptions should not be bypassed with
bot approvals, alternate accounts, synthetic contributors, or placeholder
releases.

GitHub immutable releases should be enabled in hosted repository settings so
published release assets and their tag cannot be modified.

TestPyPI promotion requires exact SHA-256 equality with the privately reviewed
release payload, GitHub build-provenance verification, cryptographic
attestation verification, and clean-install smoke tests on every supported
Python version. Because the attestation client's direct-URL mode accepts only
the production distribution host, the workflow retrieves each provenance
object from TestPyPI's Integrity API and verifies it against the corresponding
reviewed local distribution. Integrity API, identity, digest, signature, and
certificate errors all fail closed.

## Owner and organization gates

Some controls cannot be configured from this repository alone:

- organization-wide Actions policies, runner groups, and required workflows;
- billing- or plan-dependent secret-scanning validity checks;
- enterprise security policy and outside-collaborator restrictions;
- environment reviewers and production deployment approvals.

These remain administrator-owned follow-up gates and must not be represented
as locally complete merely because repository workflows pass.

## Runtime dependency agreement

The reviewed runtime set in `specs/dependency-runtime-policy.json` binds PyPI,
Conda requirements, tox Polars/Arrow floor/latest lanes and dependency previews.
Run `.venv/bin/python scripts/check_packaging_dependencies.py .` to reject drift.
Polars `>=2.1.0,<3` and Arrow `>=26.0.0,<27` retain the qualified Python 3.15.2
surface; scientific core bounds remain unchanged. Published requirements omit
pandas and xarray. The explicit, unpublished `producer-tests` group supplies
external producer/oracle tests and stays outside default and wheel installs.
Test setup uses `uv sync --extra ci --extra dev --group producer-tests`.

Conda's immutable published source pin remains a separate release handoff.
Dependency agreement and a clean wheel are not native Conda build acceptance.

## Pandas-free enforcement

The required lint lane runs `.venv/bin/python scripts/check_pandas_free.py
--source voiage`. It rejects direct pandas/xarray import nodes in every Python
source and type stub, including lazy, unreachable and type-only imports. It has
no file exclusions and does not honor `noqa` or suppression pragmas. Templates
and metadata strings are not import nodes; their separate repository-reference
gate remains Phase 7.

`tox run -e pandas-free` installs the real wheel with no extras, dependency
groups or test dependencies. A fresh isolated Python 3.15.2 subprocess verifies
that neither legacy distribution is installed and neither module is loaded by
`import voiage`. It checks the package path against the tox environment to
reject source shadowing. Negative controls demonstrate actual rejection.
Linux, macOS and Windows CI use that same lane. The bootstrap's unpublished
`verification` group contains only locked tox tools and is separate from the
no-extras target environment and the producer-test group.

The existing protected `Lint & Type Check` job invokes the source rule directly,
and `Unit Tests (Python 3.15.2)` also executes the no-extras tox lane. These
checks therefore remain part of the current required status contexts; no
branch-protection relaxation or new-job registration is needed.

## External producer acceptance

The default `producer-compatibility` tox lane tests the installed base wheel
with pytest and the unpublished `producer-tests` group. Isolated Python,
importlib-mode collection and a narrow conftest boundary keep checkout imports
out of that lane; both its main and fresh child processes verify the package
location. Real caller-created frames exercise frozen row/binding/digest results,
nullable and sliced inputs, buffer identity, import ownership and stable errors.
Negative controls prove the runtime-import watcher detects reintroduced imports.

The existing protected unit job and Linux/macOS/Windows base-runtime matrix run
this lane alongside `pandas-free`. The latter retains its separate environment
with no producer tooling. Observed numeric buffer sharing does not change the
existing strict-copy policy or claim that every conversion is zero-copy.

## Complete reference policy

Both protected lint and local tox run `scripts/check_reference_policy.py`. It
scans every Git-tracked text file, including notebook JSON, generated-code
strings and workflows. Exact reference-line fingerprints include occurrence
counts, so an approved producer test cannot hide an added or duplicated
reference. Whole-file hashes protect immutable historical evidence. Deleted
permissions, changed evidence, unsafe paths and empty scans fail closed. No
path globs, suppression directives or automatic refresh command are supported.

The producer-compatibility scope includes the existing external Parquet metadata
key, explicit test-tool declarations and executable absence controls. These
narrow permissions preserve caller behavior; the runtime AST import ban still
has no exemption. Old source-bound HPC inputs remain unchanged and independently
validated; current candidate declarations have separate unfulfilled native
source/solver/build/installed-module gates.

## Build-capacity observations

The obsolete fixed EasyBuild replay admission floor has been removed from the
current candidate. Current sizing and the
accepted support scope are tracked by B6-CAP1–B6-CAP4; G04.4/G04.5 own
common instrumentation and ordinary verification calibration.

The guard accepts `--workload-id`, `--cache-state` (cold, warm, mixed or unknown),
`--identity-file` (a JSON object describing feature/toolchain configuration),
repeatable `--artifact-dir` and repeatable `--disk-path`. Disk paths must exist;
artifact directories may be absent before a build. It records source/configuration
hashes, interpreter identity, start/end/minimum filesystem free space and
before/after directory allocation. Declare cache state honestly; do not purge
shared caches. Pass explicit cache/temporary volumes via `--disk-path` when needed.

Filesystem samples deduplicate device IDs and run at the existing guard interval.
Directory scans occur only before launch and after termination, before successful
private-temporary cleanup. Failed runs retain their private temporary evidence.
Snapshots are not peaks; filesystem deltas include unrelated activity and sampled
peaks may miss spikes. Directory allocations can include shared blocks and must
not be summed across overlapping roots. A VM needs separate host-backing evidence;
this guard alone never claims physical-capacity qualification. Monitoring failures
remain failures even when the child command succeeded.

## Retained native qualification environments

Renovate excludes the exact Cargo manifest at
`conductor/tracks/scientific_ecosystem_alignment_20261029/installed-adapters/native/Cargo.toml`
from its Cargo manager. This manifest belongs to the retained 1 November 2026
qualification packet. Its locked replay requires the exact external Innovate
source checkout documented in that packet; an ordinary maintenance checkout
does not contain those inputs.

The exclusion preserves the recorded environment and prevents an unrelated
lockfile refresh from failing on an absent replay input. The Cargo setting
retains Renovate's standard ignored directories because `ignorePaths` replaces,
rather than extends, the inherited list. Current workspace manifests and the
rest of the scientific-alignment track remain eligible for maintenance.

Qualify newer adapter inputs in a separately identified packet. Keep the
historical manifest, lockfile, source pins and receipts unchanged. This
maintenance scope does not waive dependency review, security scans, the
minimum release age, or any required local and hosted checks. The Rust
supply-chain workflow separately audits the retained Cargo lock against current
RustSec advisories and treats warnings as failures.

The default Rust lock retains `proptest` 1.11 for the workspace's Rust 1.85
minimum; Renovate holds its automated updates below 1.12. A separate
`rust/locks/proptest-current/Cargo.lock` selects Proptest 1.12 for current Rust.
CI checks the current lock with the same workspace tests, Clippy, coverage floor,
and supply-chain policy while retaining the default lock's existing checks.
Refresh the current lock with Cargo 1.100 or newer and the 14-day release-age
policy, and retain the default lock until a separately reviewed MSRV change.
From the repository root, the current lock can be refreshed with:

```sh
cp rust/Cargo.lock rust/locks/proptest-current/Cargo.lock
CARGO_RESOLVER_LOCKFILE_PATH="$PWD/rust/locks/proptest-current/Cargo.lock" \
  CARGO_REGISTRY_GLOBAL_MIN_PUBLISH_AGE="14 days" \
  cargo update --manifest-path rust/Cargo.toml -p proptest --precise 1.12.0
```

Run the current-lock CI checks after refreshing it; this command does not change
the default lock or replace the required hosted checks.
